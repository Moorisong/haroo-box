# 하루상자 통합 리드 수집 컨벤션 v2.0

> **유일한 실행 프롬프트:** `lead_collection_convention.md 지침대로 진행해`
>
> 실행 승인 범위는 **공개 리드 탐색·검증·중복 검사·기존 Google Sheets 탭 신규 행 저장·재조회**다. **이메일/DM 작성·발송은 절대 포함되지 않는다.**
>
> 주요 운영 목표: 사용자의 개입 없이, **현재 영업 스프레드시트에 존재하는 모든 지원 대상 채널 탭**을 같은 품질 기준으로 채우되, 탐색·검증은 병렬화하고 저장은 충돌 없이 조정한다. 목표 미달은 정확히 보고한다. **High 모드라고 해서 실행 시간·토큰·검색 호출 한도가 무한해지는 것은 아니다.**

## 0. 실행 범위와 설정 우선순위

1. GitHub `Moorisong/haroo-box`의 **dev** 브랜치에서 이 파일과 `project_docs/lead_collection_config.yaml`, 등록된 채널 문서를 읽는다. 누락 시 추측하거나 기본 브랜치를 대신 읽지 않는다.
2. Google Sheets 메타데이터로 **실제 전체 탭 목록과 헤더**를 읽는다. `channels`에 없는 탭 중 영업 리드 탭이 있다면, 헤더·내용·발송 이력 구조를 판별하고 기존 채널 규칙으로 안전하게 매핑 가능한 경우에만 자동 포함한다. 매핑 불가 탭은 변경 없이 별도 상태로 보고한다. 비리드/관리 탭은 변경하지 않는다. 단순히 추가 탭이 있다는 이유로 이미 검증 가능한 다른 채널을 중단하지 않는다.
3. 사용자 이번 요청의 명시적 설정 > `lead_collection_config.yaml` > 채널 문서의 기본값. 한 줄 프롬프트는 설정 파일의 기본 타깃·지역·서비스·목표를 모두 승인한 수집 실행 요청이다. 이미 확정된 조건을 묻지 않는다.
4. 현재 설정 기준 기본 활성 채널은 `email`, `ig`다. **모든 등록 활성 탭을 각기 목표 건수만큼 채우는 것이 완료 조건**이다. 이메일이 우선순위가 높다고 IG를 굶기지 않는다. 목표 건수는 서로 대체하거나 합산해서 달성했다고 표시할 수 없다.
5. 문서/시트 열 구조 불일치 발생 시 실제 헤더를 우선한다. `A:F`의 의미와 `G:I` 접촉 기록이 명확한 `email`과 `ig`는 매핑이 확정되어 있으므로 **다시 질문하거나 구조 불일치로 중단하지 않는다**. 매 실행 헤더가 바뀌었는지 검증한다.

## 1. 실제 2026-11-26 확인된 데이터 구조 — 기존 탭을 변경하지 말 것

공통적으로 A~F **신규 리드 수집 영역**, G~I **접촉 발송 기록**이다. 열을 추가·삭제·재배치·덮어쓰지 않는다. 헤더가 실제로 다르면 새 구조를 식별한 뒤 충돌 없는 열만 사용한다.

| 채널 | A | B | C | D | E | F | G | H | I |
|---|---|---|---|---|---|---|---|---|---|
| email | 구분 | 이름 | 지역 | 국내/해외 | 연락처 (공식 사이트/Contact URL) | 이메일 (공식 업무용) | 1차 이메일 | 2차 이메일 | 3차 이메일 |
| ig | 구분 | 이름 | 지역 | 국내/해외 | IG 계정 (@username) | IG URL (공식 프로필) | 1차 DM | 2차 DM | 3차 DM |

**저장은 A~F에만 수행하며 G~I는 쓰기 범위에서 아예 제외한다.** 공란으로 덮는 것도 금지. 확인된 공식 연락처·최근 활동·적합성·검증일 등 A~F에 없는 증빙은 공식 출처 URL과 날짜를 **해당 신규 리드의 F 셀 메모**에 기록한다. 메모 기능이 지원되지 않는 환경이라면 검증 로그를 별도로 결과에 남기며 증빙이 사라진 상태로 검증 완료라고 주장하지 않는다. 시트 제목/열 확장은 사용자 별도 승인 없이는 금지한다.

## 2. 실행 전 1회 프리플라이트 (짧고 확실하게)

1. 목표 시트 메타데이터와 각 탭의 실제 A1:I1 헤더 조회, 현재 마지막 **비어 있지 않은 데이터 행** 확인. 사전에 입력된 보고 수치만 신뢰하지 말고 조회한다.
2. 모든 영업 채널의 A~I 기존 레코드와 발송 이력을 읽고 정규화 인덱스를 **한 번 구축해 재사용**한다. 대용량 조회는 도구 한도 내 **범위 분할**한다. 모든 셀을 매 후보마다 반복 조회하지 않는다.
3. 조건·국가·활성 채널·목표·동일 단체 재접촉 제외 기준 확인.
4. 각 채널 수집에 필요한 데이터 읽기·쓰기·메모 작성 도구 접근성 확인. 메모 작성 불가 시 별도 추적 가능한 검증 기록 경로를 사용. 미지원 탭만 보류하며 지원 탭은 계속한다.

## 3. 공통 검증 기준 (모든 채널 동일)

- 공식 단체명과 국가·지역, 실제 운영 여부, 하루상자 타깃 적합성을 확보한다.
- **최근 12개월 내 날짜가 명시된 공식 활동 근거 1건 이상** 필수. 미래 일정은 공식 발표일 또는 최근 운영 근거로 현재 활성성을 구분해 기록한다. 검색 색인일, 저작권 연도, 날짜 없는 소개는 증빙이 아니다.
- 직접 적합: 어드벤트/크리스마스/연말 참여형 활동, 높은 적합: 청소년·가족·공동체 행사, 잠재 적합: 관련 교육·비영리 캠페인. 구체적 근거가 없는 범용 단체는 제외.
- 이메일: 공식 사이트에 공개된 업무용 이메일, 공식 이메일 출처 URL 확인. 인스타그램: 해당 단체 공식 사이트의 계정 링크 또는 공식 공개 프로필로 연결 입증. 핸들 추측·개인 계정·비공개 근거는 제외.
- 이메일 주소의 공개 확인과 수신 가능성, 인스타 계정의 공식 확인과 DM 수신 가능성은 구분한다.
- 추적 데이터: 단체명·지역·채널·공식 홈페이지·채널 연락처/프로필·연락처 출처·활동 근거 URL/날짜·적합성 이유·검증일·중복 판정 결과. 필수 근거 누락된 행은 저장하지 않는다.
- 웹사이트 접근 제한·robots.txt·서비스 약관·개인정보 보호·합리적 요청 빈도를 지킨다. 자동 발송은 별도 승인을 받아도 이 수집 실행 내에서는 수행하지 않는다.

## 4. 병렬 탐색 + 중앙 조정 저장 (기본 실행)

**병렬화는 목표이지 동시 작업 생성 보장이 아니다.** 환경에서 병렬 작업이 가능하면 다음 정책을 사용하고, 불가능하면 채널을 번갈아 짧은 배치로 처리한다. **탭별 개별 실행을 강제하지 않는다.**

1. 초기 기존 DB 인덱스를 공통으로 공유한다. 채널별로 독립 **탐색/검증 큐**를 둔다. 가능한 경우 채널당 최대 2개 조사 작업, 전체 최대 4개로 시작한다. 무조건 4개 병렬 호출을 만들지 않고 도구의 동시 실행 지원·속도 제한에 맞춰 조절한다.
2. **공통 소스 재사용:** 공식 단체 사이트·행사·최근 활동은 한 번 확보해 모든 큐에서 재사용. 이메일과 IG별 연락처 검증만 분기한다. 동일 후보를 두 큐가 다시 조사하지 않게 임시 공통 후보 등록부를 유지한다.
3. **채널별 공정성:** 처음부터 email/ig를 각각 탐색하고 검증한다. 한 채널에서 후보가 안 나와도 다른 채널을 중단하지 않는다. 목표가 남아 있는 채널에 탐색 예산을 집중한다. 한 채널의 1~2건 저장 성공을 전체 실행 완료 또는 일시 중단 근거로 사용하지 않는다.
4. **검색 범위:** 국가 × 도시 × 단체 종류 × 행사/프로그램 키워드로 분할. 기존 DB 중복률이 높으면 즉시 도시·국가·단체 유형·검색어를 교체한다. 기존 687개 이메일, 72개 IG라는 과거 수치는 참고만 하며 실행 시 재조회한다.
5. **적응형 후보 풀:** 첫 라운드는 채널당 20~40 후보를 탐색하고, 목표 건수에 따라 라운드를 확장한다. 후보 탈락률을 이용해 다음 라운드 크기를 조정한다. 전체 후보 2N 확보 전에도 5~20건의 검증 완료 리드가 있으면 안전하게 먼저 저장한다.
6. **중앙 중복 레지스트리:** 정규화한 단체명+국가/도시, 공식 도메인, 공식 계정, 이메일을 비교한다. 공유 도메인·유사 명칭만으로 무조건 중복 처리하지 않는다. 기존 모든 채널 및 이번 실행 후보/저장분 확인. 수신 거부·접촉 제외 및 발송 이력 있는 단체는 임의 재접촉 대상으로 만들지 않는다.
7. **채널 배정:** 동일 단체는 **기본적으로 한 채널에만 신규 등록**. 이메일 우선순위를 절대 규칙으로 적용하지 않는다. 양쪽 모두 유효하면 **목표 충족률이 낮은 채널**, 동률이면 설정 우선순위로 배정한다. 기존 타 채널에 등록된 동일 단체는 접촉 전이어도 별도 승인 없으면 교차 채널 신규 등록하지 않는다. 목표 충족을 위해 중복 기준을 완화하지 않는다.
8. **쓰기 단일 조정자:** 서로 다른 탭을 대상으로 하더라도 단일 실행 안에서는 한 조정자가 순차로 배치 쓰기, 저장 전 중복 인덱스 갱신, 마지막 데이터 행 재확인, 저장 후 재조회 수행. 병렬 조사자가 개별 시트에 직접 쓰지 않는다. 외부에서 독립 실행이 동시에 돌아가는 경우 원자적 잠금/중복 방지를 보장할 수 없으므로 중복 검사를 재수행한다.
9. 도구 요청 실패 시 실제 저장된 행부터 조회 후 필요한 부분만 안전하게 재시도한다. 중복·열 충돌 또는 쓰기 실패는 문제 채널만 멈추고 다른 안전한 채널은 계속한다.

## 5. 채널별 저장 정책

- email은 A~F에 `구분/이름/지역/국내외/공식 사이트 또는 Contact URL/공식 이메일`.
- ig는 A~F에 `구분/이름/지역/국내외/@계정명/정규화된 https://www.instagram.com/<username>/`.
- G~I는 절대 변경하지 않는다. 메모는 **신규 행 F 셀**에 기록한다. 발송 열·헤더·기존 행 메모도 건드리지 않는다.
- 데이터 행 바로 뒤에 필요한 만큼만 추가한다. 시트 격자 크기(할당된 빈 행 수)와 실제 마지막 데이터 행을 혼동하지 않는다. 수식/서식/유효성 검사 원본 보호, 기존 행 보존 확인.
- 목표 20건이라도 **1건 단위 검색·쓰기·보고를 반복하지 않는다**. 최소한 조사 배치를 묶고 쓰기 5~20건 또는 가능한 안정적 묶음으로 처리한다.
- 저장 후 실제 A~F 값, F 메모, 채널 간 중복, 이전 데이터 및 G~I 발송 기록 미변경을 검증한다.
- 도구가 F 메모를 쓰지 못하거나 읽지 못하면 검증 로그에 출처를 남기고, 보고서에 해당 제한을 명시한다. 리드의 공식성/활동 근거 검증 자체는 생략할 수 없다.

## 6. 반복·종료·보고

채널별 상태를 `목표/탐색 후보/중복/연락처 미확인/활동 미확인/적합성 부족/검증 완료/저장/재조회/남은 수량`으로 유지한다.

매 라운드마다: (a) 후보 수집 → (b) 검증 → (c) 저장 가능한 묶음이 생기면 배치 저장 및 재조회 → (d) 부족 채널 검색 확장. 검색 하나 실패하거나 한 배치 저장 성공했다고 중단하지 않는다.

최종 보고는 반드시 채널별 목표와 실적 및 **실제 신규 데이터 행 범위**, 소스 증빙 방식, 제외 수량, 시도한 검색 범위, 기존 행/발송 기록 보존 여부를 포함한다. **검증 완료**와 **시트 저장/재조회 완료**를 구분. 2/40 같은 미달을 성공으로 표현하지 않는다.

**중단 사유는 관측한 사실**로만 작성한다. 예: 특정 도구의 권한 오류, 호출 상한, 접근 제한, 검색 공간을 합리적으로 확장했음에도 미확인. 단순히 시간이 걸림/중복 많음/소수 건 저장했음은 단독 중단 사유가 아니다. 실행이 실제로 종료되어야 한다면 채널별 미달 수량과 다음 실행에서 재개할 탐색 범위를 남기고 부분 완료로 보고한다.

## 7. 별도 실행과 확장

- 기본 한 줄 명령은 **모든 지원 채널**을 대상으로 한다.
- 선택 실행 예시: `lead_collection_convention.md 지침대로 email 탭만 진행해`, `... ig 탭만 진행해`. 이때 **전체 탭은 중복/발송 기록 확인을 위해 읽지만 선택 탭에만 쓴다.**
- 현재 지원되지 않는 신규 탭을 발견하면 데이터 구조를 추론해 안전하게 쓸 수 있을 때만 진행한다. 새 채널 고유 확인 규칙이 필요하면 신규 채널 문서와 config 등록을 먼저 권고하고, 다른 채널의 실행은 중단하지 않는다.
- 하나의 High 모드 채팅만으로 확정된 40건을 매번 채울 수 있다고 보장하지 않는다. 대규모 확장·정기 자동 수집·원자적 잠금은 별도 실행 프로그램/워크플로가 더 적합하다. 문서만으로 진짜 백그라운드 처리 또는 무제한 병렬 수집을 만들 수 없다.
